# 海风哨真实数据与更新链路设计

确认日期：2026-10-18  
状态：已确认

## 设计目标

建立可验证、可回退、可观测的数据链路，避免把“定时任务已配置”误认为“页面数据一定实时”。用户看到的每项关键数据都必须能够回答来源、实况时间、抓取状态和页面发布时间。

## 平台约束

GitHub Actions 定时工作流可能因平台负载延迟或被丢弃；公共仓库长期没有活动时，定时任务还可能被自动禁用。

官方说明：https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows

因此，对外文案统一为：

> 系统计划约每 15 分钟检查一次，实际更新时间以页面显示为准。

不得承诺每 15 分钟准时更新或严格实时。

## 1. 当前链路问题

### `fetchedAt` 语义不准确

当前脚本在上游业务数据没有变化时保留旧文件，因此 `fetchedAt` 更接近“最后一次数据变化并写入文件的时间”，不能直接表示最近一次成功检查时间。

### 年度查询存在边界

当前只查询上海时区的当前年份，跨年时可能遗漏上一年度仍在活动的台风。

### 字段语义存在假设

- `warnlevel` 未验证便被当作属地官方预警；
- `endtime` 的字段含义尚未得到确认；
- 找不到“中国”预测时会静默采用第一个机构；
- 未保存所有预测机构的路径和选择依据。

### 抓取、提交和部署耦合

当前通过“抓取、变化时提交、再次检出、部署”完成发布，增加了时间元数据陈旧和部署内容与本次抓取结果不一致的可能性。

## 2. 时间模型

数据结构至少区分：

| 字段 | 含义 |
| --- | --- |
| `checkedAt` | 系统最后一次尝试检查上游的时间 |
| `lastSuccessfulFetchAt` | 最近一次成功获得且通过基础校验的响应时间 |
| `sourceObservedAt` | 来源提供的最新实况时间 |
| `publishedAt` | 当前页面数据完成部署的时间 |

页面不得将这四个时间合并成一个模糊的“更新时间”。

## 3. 数据健康状态

| 状态 | 含义 |
| --- | --- |
| `healthy` | 抓取成功，数据完整并通过校验 |
| `unchanged` | 抓取成功，上游业务数据暂无变化 |
| `delayed` | 抓取成功，但来源实况超过预期周期未更新 |
| `partial` | 部分台风、预测机构或字段缺失 |
| `failed` | 本次抓取失败，继续使用最后有效数据 |
| `stale` | 最后有效数据已经超过允许时间 |
| `invalid` | 来源响应成功但无法通过结构或业务校验 |

前端必须分别展示采集链路状态和来源实况新鲜度。“来源暂无变化”不得被当成“网站抓取失败”。

## 4. Schema v2

目标结构：

```json
{
  "schemaVersion": 2,
  "status": {
    "state": "healthy",
    "checkedAt": "2026-10-18T00:00:00.000Z",
    "lastSuccessfulFetchAt": "2026-10-18T00:00:00.000Z",
    "publishedAt": "2026-10-18T00:02:00.000Z",
    "usingCachedData": false
  },
  "sources": [],
  "storms": [],
  "localWarnings": [],
  "notice": ""
}
```

每个数据来源至少记录：

- 来源标识和名称；
- 官方页面和接口地址；
- 数据用途；
- 最后检查时间；
- 最后成功时间；
- 来源最新实况时间；
- 当前状态；
- 字段或使用限制说明。

## 5. 台风数据模型

每个台风保留：

- 编号和中英文名称；
- 活动态及其来源字段；
- 最新实况；
- 完整历史路径；
- 按预测机构分组的预测路径；
- 来源系统关注标记；
- 字段缺失情况；
- 数据验证结果。

调整规则：

- `warningLevel` 改名为 `sourceAttentionMark`；
- `sourceAttentionMark` 不进入属地官方预警模块；
- 预测路径保留机构身份；
- 找不到中国预测时可以展示其他机构，但必须明确名称；
- 不静默改变预测机构；
- 属地官方预警使用独立的 `localWarnings` 结构。

## 6. 抓取与部署流程

目标流程：

```text
定时或手动触发
      ↓
读取当前与上一年度列表
      ↓
合并并去重活动台风
      ↓
抓取台风详情和各机构预测
      ↓
标准化并校验数据
      ↓
生成状态与时间元数据
      ↓
保留有意义的数据快照
      ↓
直接部署本次验证通过的工作目录
```

流程约束：

- 每次成功检查都更新运行状态；
- 业务数据变化时才形成新的业务快照；
- 部署使用本次已验证文件，不重新检出可能不同的版本；
- 抓取失败时不覆盖最后有效台风数据；
- 失败状态可以与最后有效数据一起部署；
- 保留 `workflow_dispatch` 手动触发入口；
- 数据提交和自动部署避免产生递归触发。

## 7. 定时策略

建议将任务错开整点高峰：

```yaml
schedule:
  - cron: '7,22,37,52 * * * *'
```

该配置代表计划频率，不代表服务等级承诺。

## 8. 数据校验

部署前至少验证：

- JSON 顶层结构和 Schema 版本；
- 台风编号、名称和数据来源存在；
- 经纬度为数值且位于合法范围；
- 实况时间可解析并按时间顺序排列；
- 最新实况与路径最后有效点一致；
- 预测点时间晚于最新实况；
- 风力、风速、气压和移动速度字段类型合理；
- 重复路径点得到识别和处理；
- 活动态和来源字段不存在明显冲突；
- 每组预测路径带有机构名称；
- 未验证字段不进入用户结论。

严重结构错误阻止新数据覆盖旧数据；次要字段缺失则标记为 `partial`。

## 9. 跨年与多台风

- 同时查询当前年份和上一年份；
- 按台风编号合并去重；
- 保留全部活动台风；
- 无活动台风时才回退到最近一场已停编台风；
- 多台风时不简单使用接口第一项；
- 默认展示对象由属地官方预警、预测最近点、当前距离和数据新鲜度共同决定。

## 10. 缓存与最后有效数据

- 前端避免直接使用无法判断版本的旧浏览器缓存；
- 当前 JSON 带有 Schema 和发布时间；
- 数据更新失败时继续展示最后一份通过校验的数据；
- 明确显示“正在使用缓存数据”和最后成功时间；
- Service Worker 不得在无提示的情况下长期返回旧台风数据；
- 新旧 Schema 切换失败时回退到安全错误状态。

## 11. 可观测性

至少记录和检查：

- 定时任务最后触发时间；
- 最近成功抓取时间；
- 连续失败次数；
- 各来源响应状态；
- 数据结构异常；
- 最新实况年龄；
- 部署状态；
- 当前是否使用最后有效数据。

建议连续两次抓取失败后产生仓库通知，恢复后同步标记恢复。另行监控计划任务是否因仓库长期无活动而停用。

## 12. 实施顺序

1. 定义并验证 Schema v2；
2. 重构时间字段和来源结构；
3. 增加跨年、多台风和多机构处理；
4. 增加数据校验器及测试样本；
5. 重构 GitHub Actions 抓取和部署步骤；
6. 增加失败回退与状态文件；
7. 修改前端读取与状态展示；
8. 执行手动触发、无变化、上游失败和异常结构演练。

## 验收标准

- 页面区分检查时间、成功抓取时间、实况时间和发布时间；
- 来源未变化不会被误报为抓取失败；
- 抓取失败不会覆盖最后有效数据；
- 缓存数据具有明确标识；
- 当前与上一年度活动台风均可被发现；
- 多个活动台风不会被遗漏；
- `warnlevel` 不再作为属地官方预警；
- 每条预测路径保留机构信息；
- 异常数据无法进入用户结论；
- 定时任务延迟或停止能够被识别；
- 页面不承诺严格的 15 分钟实时更新。
